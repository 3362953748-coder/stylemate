## 一、产品定位

市面上的 AI 写作工具已经能做好「小红书改写」「邮件润色」「翻译」这些**通用能力**——
真正的稀缺性不在单次改写,而在**风格的沉淀与复用**:

| 通用写作工具 | StyleMate |
|---|---|
| 每次改写,风格由预设标签决定 | 从你的范文里学出风格,越用越准 |
| 输出一次性,用过即弃 | 风格模板沉淀为资产,可反复调用 |
| 「活泼/专业」这类模糊描述 | 句长、人称、修辞、结构等可观测特征 |

**核心闭环**:上传范文 → AI 分析风格 → 保存模板 → 日常改写 → 收藏结果 → 再次使用

## 二、核心功能

### 1. 多场景文案改写
四种内置风格,各自匹配真实使用场景:

| 场景 | 风格特征 |
|---|---|
| 📕 小红书 | 自然口语化、朋友式分享、适度 emoji、不堆砌营销热词 |
| 📧 正式邮件 | 称呼得体、结构清晰(事由/正文/致谢)、简洁不寒暄 |
| 📄 公众号 | 小标题与过渡句、观点明确、兼具理性与感染力 |
| 🌐 英文表达 | 地道自然、避免中式直译、句式多样自信 |

叠加**三维语气调节**:正式程度(1-5)、情绪浓度(1-5)、表达长度(简短/适中/详尽)。
数值会被翻译成自然语言指令注入 prompt,而非直接映射到采样参数——
因为「正式程度 3」是写作意图,不是 temperature。

### 2. AI 专属风格模板(核心差异化)
上传 3～5 篇范文,AI 两步提取:

**第一步 · 逐篇特征提取**(对每篇独立调用)
句长特征、人称使用、情绪基调、用词特点、句式套路、修辞技巧、节奏感、整体结构、标志性特征。

**第二步 · 汇总归纳**(跨篇综合)
生成风格名、风格描述、五维特征标签,以及一段 **150～250 字可直接执行的中风指令**。

> 为什么要分两步?一次性对多篇长文做整体分析,模型容易泛泛而谈。
> 先逐篇建立可观测的事实,再让模型从事实归纳出风格,结论更具体、更可执行。

实测输出示例(3 篇范文 → 归纳结果):

```
风格名称:松弛日常白描体
语言风格:口语化日常语,朴素直白,偶有中英混用,几乎无比喻夸张,白描写实
句式特点:短句为主,单句多在 15-25 字内,长短交替,动词串联动作链
用词习惯:日常词汇如「最爽」「拧巴」「解压」,数字量化细节,无华丽词藻
情绪表达:平和满足,松弛小确幸,带自嘲式幽默,用身体感受替代直白评价
文章结构:首句点题后逐项展开,每段一事,结尾以轻口语或具体小细节收束
```

风格指令会捕捉到**隐性写作习惯**(如「评价物件时用身体感受代替形容词」),
这正是通用改写工具给不出的部分。

### 3. 风格强度调节(0–100%)

用户既怕「太像自己的旧文」显得抄袭,又怕「不够像」失去个性 —— 这是一个连续取舍,
多数工具只给一个「更像我」的开关。

StyleMate 把强度拆成五档语义,注入改写指令:

| 区间 | 语义 |
|---|---|
| 0–20% | 只做轻度润色,保持中性通用 |
| 21–45% | 仅借鉴语气倾向,不复现句式与词汇习惯 |
| 46–70% | 体现部分特征(用词偏好、句长节奏),保留原文骨架 |
| 71–88% | 充分体现风格特征,但内容须原创、不得雷同 |
| 89–100% | 完全以该风格组织表达,内容必须全新 |

实测(`scripts/verify-intensity.mjs`):同一段素材,20% 强度一致性 12 分,
95% 强度 62 分 —— 输出从标准产品说明口吻变为第一人称短句随笔。

### 4. 风格一致性自评

生成后对照目标风格逐条打分,输出 0–100 分与改进建议。
这是竞品调研中几乎全部缺失的能力 —— 此前只能靠人眼判断风格是否到位。

> **评分口径的设计修正**:只评**文风层面**(句长节奏、用词习惯、语气、结构),
> 不评内容题材。初版评分器要求「改成第一人称日常叙述」,导致输入产品参数时
> 给出 8–10 分的失真结果;修正后同一组样本低强度 12 分 / 高强度 62 分,
> 分数才真正反映文风差异。

### 5. 多版本对比生成
同一段内容**并行**生成三个取向:

| 版本 | 取向 |
|---|---|
| A 版 | 简洁专业 —— 结构清晰、信息克制 |
| B 版 | 自然亲切 —— 口语自然、有温度 |
| C 版 | 情绪感染力强 —— 节奏感强、易共鸣 |

并排卡片对比,点击选中后可对单个版本继续微调,避免"要么全接受要么全推翻"。

### 6. 历史记录与风格库
- 云端持久化改写记录、收藏、风格模板
- 支持编辑/删除模板、收藏切换、"复用"回填原文与语气设置
- 按用户隔离,换设备可继续使用

## 三、技术方案

```
React 19 + TypeScript + Vite
        │
        ├── cloud.ts ──────── 单一云客户端(endpoint + publishableKey)
        │
        ├── llm.ts ────────── LLM 服务层
        │     ├── analyzeStyle()   两步式风格提取
        │     ├── rewriteText()     流式改写(可中断)
        │     ├── generateVariants() A/B/C 并行生成
        │     └── refineText()      局部微调
        │
        ├── storage.ts ────── 数据访问层(强类型, auth 门禁)
        └── database.types.ts ── 与云端表结构对应的 schema 类型
```

**后端**:Serverless BaaS(免密钥 LLM 调用 + 托管 PostgreSQL + OAuth 登录)。
用户无需自备任何 API Key,前端只持有可公开的 `publishableKey`。

**数据模型**(两张表,均按 `owner_id` 做行级隔离):

```sql
style_templates     -- 风格模板:特征 JSONB + 可执行风格指令
rewrite_records     -- 改写记录:原文/结果/场景/版本/语气/收藏标记
```

RLS 策略遵循 `DEFAULT auth.uid()` + `WITH CHECK (owner_id = auth.uid())` 双保险:
客户端永远不发送 `owner_id`,由数据库填充并校验,防止越权伪造。

**几个实现上的取舍**:

- **流式是唯一选项** —— 云端只支持 `stream: true`,所以一次性任务(风格分析、结构化输出)
  也走流式,自己收集增量后解析 JSON。
- **JSON 解析做了兜底** —— 模型偶尔会裹 markdown 围栏或前后带解释文字,
  因此先剥围栏,失败则回退到提取最外层花括号。
- **模型分用途择优** —— 风格分析要求稳定输出 JSON,改写要求语言表现力,
  分别从模型目录里挑,而不是一律取第一个。
- **Prompt 注入防护** —— 用户文本被包在 `"""` 分隔符内,与指令明确区隔。

## 四、可验证的联调脚本

`scripts/` 下有四个脚本,对应四条关键链路,均可独立运行:

```bash
node scripts/verify-llm.mjs             # 模型目录 + 流式改写 + JSON 结构化输出
node scripts/verify-style-analysis.mjs  # 多范文风格分析完整流程
node scripts/verify-template-loop.mjs   # 风格模板对改写的实际约束效果
node scripts/verify-intensity.mjs       # 风格强度调节 + 一致性自评
```

第三个脚本会输出**同素材在「无模板」与「套模板」下的改写对比**,
用于证明风格模板真的起作用,而不只是界面上的一个标签。

第四个脚本输出**低强度 vs 高强度的改写与一致性评分对比**(实测 12 分 vs 62 分),
证明强度控件不是摆设。

## 五、简历写法

**项目名称**:StyleMate · AI 个性化文案风格助手

**技术栈**:React 19 + TypeScript + Vite / LLM 风格特征提取 / Prompt Engineering / PostgreSQL 行级安全(RLS)

**可量化的能力点**:

1. **需求分析** —— 通过案头研究定位问题域:88% 用户使用 AI 写作但仅 25% 感知到效果,
   「听起来泛泛」以 87 票成为第一痛点。据此判断差异化在**风格资产沉淀**而非改写质量。
2. **AI 产品设计** —— 设计两步式风格提取(逐篇特征提取 → 跨篇归纳),
   规避长文本整体分析易泛化的问题;输出九项可观测指标 + 五维特征 + 可执行风格指令。
3. **从竞品缺口反推需求** —— 调研发现「风格浓度调节」与「一致性自动检测」是竞品空白,
   据此迭代 v1.1,实测低强度 12 分 / 高强度 62 分,证明控件真实生效。
4. **体验设计** —— 多版本并排对比、选中后局部微调;一致性检测输出可操作的改进建议,
   而非空泛评分。
5. **数据安全设计** —— 采用 RLS 行级安全实现用户数据隔离,
   `owner_id` 由数据库默认值填充,客户端不可伪造;UPDATE 策略同时约束 `USING` 与 `WITH CHECK`,防止行转赠。

**面试时如何谈调研边界**(建议主动说明):

> 本项目的用户研究处于**案头研究阶段**。我基于公开行业报告与竞品评测定位了三个待验证假设 ——
> 风格感知度不足、风格资产零沉淀、抄袭与个性化之间缺少控件 —— 并用可运行原型做了验证性测试。
> 一手访谈与定量问卷是下一步计划,验证方案已写在 `docs/user-research.md`。

**建议补充的行为数据**:

| 指标 | 定义 | 目标 |
|---|---|---|
| 模板创建率 | 注册用户中创建 ≥1 个模板的比例 | ≥ 25% |
| 模板复用率 | 模板被调用 ≥1 次的比例 | ≥ 60% |
| 直接采纳率 | 生成后未修改即保存的比例 | ≥ 50% |
| 次周留存 | 7 日内回访 | ≥ 30% |
| 强度调节使用率 | 用过强度滑杆的比例 | ≥ 30% |
| 一致性检测使用率 | 用过检测的比例 | ≥ 25% |

> 保存历史记录 ≠ 用户留存。只有上述行为数据能证明风格资产真正形成了粘性。

**配套材料**:`docs/PRD.md`(需求文档)、`docs/competitive-analysis.md`(竞品分析)、
`docs/user-research.md`(调研与验证计划)

## 六、本地运行

```bash
npm install
npm run dev      # 开发模式
npm run build    # 生产构建(含类型检查)
npm start        # 构建并以静态服务器启动(部署用,监听 PORT)
```

**后端配置**:仓库内置了一套公开的演示环境配置,克隆后可直接运行。
若要接入自己的实例,复制 `.env.example` 为 `.env` 并填入对应值:

| 变量 | 说明 |
|---|---|
| `VITE_CLOUD_ENDPOINT` | 后端数据面地址 |
| `VITE_CLOUD_PUBLISHABLE_KEY` | 应用标识密钥(前端可持有,服务端校验 Origin) |
| `VITE_CLOUD_OAUTH_RELAY` | OAuth 中继地址(账号 / 微信登录必需) |

> `publishableKey` 仅用于标识应用,本身不含权限,服务端会校验请求来源,
> 因此它可以安全地放在前端代码里。**服务端密钥绝不入库。**

**数据库表结构**已随环境一并创建(`style_templates` / `rewrite_records`),
均开启行级安全(RLS),按 `owner_id` 隔离。若迁移到自己的环境,需按
`src/database.types.ts` 的结构建表并配置同名策略。

### 部署

**GitHub Pages**(推荐,当前线上版本即用此方式)
仓库内置 `.github/workflows/deploy-pages.yml`,推送到 `main` 即自动构建并发布。
Pages 托管在仓库子路径下,因此构建时需注入 base 前缀:

```bash
STYLEMATE_BASE=/stylemate/ npm run build
```

> `scripts/post-build.mjs` 会生成 `404.html` 作为 SPA 回退
> (纯静态托管没有 history fallback)。

**自有服务器**
`npm start` 会构建并启动 `server.js`,该脚本读取 `PORT` 环境变量并监听 `0.0.0.0`,
自带静态资源服务、SPA 回退与路径穿越防护。

**登录回调**需要在正式域名下完成授权,故完整流程请使用线上版本。
